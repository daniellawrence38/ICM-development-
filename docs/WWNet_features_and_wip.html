Features

One combined network import

Import Network Data runs four imports in the right order, checks the model and adds it to the map once.

1

Sewers

Chambers and gravity sewers, GDA94 to GDA2020, segment chaining and tee detection

2

Pressure, optional

Pump stations and pressure mains. Runs before the join, so each inlet dead end becomes the wet well

3

Join dangling ends, 5 m

Splits the main at a missed tee and inserts a tee node

4

Pump station register, optional

Wet well floor, levels, storage and design rate from the .xlsx

Rules that matter on real data

  • Wet well: the gravity sewer end within 1 m of the pump station point. None found: a WW_ node, left unconnected with a warning
  • Rising main: starts at a main end within 30 m of the station; its discharge joins a node only within 1 m, else a D_ node to connect by hand
  • Register: matched on SAP_ID. Levels, storage and a design flow (1 duty + 1 standby) come from three sheets
  • A sewer failure stops the run; a pressure failure skips the register; a join failure does not

WWNet · features and work in progress

Built on 25 November at the user’s request to combine the imports. The order is deliberate: pressure runs before the join so the inlet dead end at each pump station is already a wet well and never gets joined to a sewer. The register sheets: Level Settings for the levels and wet well floor, Civil for storage (area = storage ÷ (alarm − overflow depth)), Motor and Pump Attributes for design flow and head. The single import tools are still there and can be re-run alone.

The first bulk import surfaced 4,028 issue rows. Most were artefacts of the source data, not the network: −99.9 sentinels read as real levels produced 118 m drops and adverse grades. The estimation order came from the user: use the invert on the other side of the node first, matched on obverts so a DN change keeps the pipe tops aligned. What is left are genuine data issues for an engineer to look at.

Features

Pump stations and rising mains

In the model

  • Wet well as a SWMM storage node
  • Pump curve, or a constant duty rate
  • Start and stop levels; duty, assist and standby
  • Rising mains as force mains: Darcy-Weisbach ks or Hazen-Williams C
  • Wet well floor below the incoming sewer invert, kept as a drop

Where the data comes from

  • Import Pressure Data: station points and main geometry; the GIS holds no hydraulics
  • Import Pump Station Data: the pump station register .xlsx
  • Set Pump Station Data: a data sheet entered by hand, or a pasted pump curve

What a run reports

  • Pump starts per hour and run time %
  • Maximum wet well level against start and overflow
  • Overflow volume (m³)
  • Rising main peak flow and velocity

Flags: any overflow · more than 10 starts/h (a screening value; it depends on motor size) · rising main velocity outside 0.7–2.0 m/s

WWNet · features and work in progress

Station hydraulics live in a separate corporate system that cannot be linked, so they come from the register workbook or a data sheet. A key fix on 25 November: the wet well node is the gravity terminal manhole, so its invert equalled the incoming sewer invert and real stop levels were rejected. The wet well floor can now be set below it. The register gives one design rate, so each station gets one duty and one standby pump at that rate; second-pump test data is a future enhancement.

Features

Existing demand from land use

Calculate Existing Demand

  1. DPLH-071 zone polygons give the area and the use
  2. Residential zones take their code from DPLH-070 R-Codes; split codes such as R20/40 use the lower code by default
  3. DS 50 Tables 4.1–4.3 give the rate. Other zones take the closest class; no match is flagged and loaded as R15
  4. About 50 sample points per polygon go to the nearest sewer within 150 m, then to its upstream node
  5. One LU- sub-catchment per node and class, plus a Land use loading layer to review

WWNet · features and work in progress

The question was how to load existing demand without a load per connection point. ICM and SWMM only take inflow at nodes, so summing per node is lossless. Method and data are the user’s choice: DPLH-071 zones for area and use, DPLH-070 for R-codes. ‘Residential development’ zones have no code in DPLH-070, so they default to R30 (339.97 ha). Roads, parks, reserves and farmland load zero. Three runs in Pro on 26 November; the third was written. Flow monitoring calibration is set aside for now.

WWNet · features and work in progress

DS 50 has no velocity criterion, so velocity is reported for information only. Two Table 4.4 entries sit slightly above the computed Colebrook capacity, which is why both are checked. The simulation default roughness changed from Manning to ks on 24 November so one roughness drives both runs. Statistics exclude the warm-up (24 h by default, 48 h runs). Features

Export to InfoWorks ICM

Nodes

  • Terminal chambers as Outfall
  • Dangling ends stay Break, with a warning
  • Missing ground levels filled from a DEM
  • Chamber floor lowered to the lowest connected invert

Conduits

  • Gravity sewers: solution model Full
  • Rising mains: ForceMain, headloss None
  • Lengths under 1 m written as 1 m
  • Long notes cut to the field length

Pumps

  • Rotpmp with a head-discharge curve, or Fixpmp at the station rate
  • Switch on and off from the start and stop levels
  • Standby pumps not exported

Sub-catchments

  • One per loaded node, no boundary needed
  • Population for residential load
  • Trade flow for commercial and industrial
  • Manual loads as additional foul flow

File geodatabase + CSV + mapping notes · system_type foul on every object · ODIC order: nodes, conduits, pumps, sub-catchments · GDA2020 or GDA94 output

WWNet · features and work in progress

Every rule here came from an ICM validation message on real data. Dangling ends stay Break because an Outfall would silently drop their flow. Chamber floors are lowered because ICM rejects a downstream invert below the node floor. The system_type fix came from ICM’s ‘node is a different system type than the subcatchment’ check. The user’s saved ODIC configs need the new fields mapped: system_type, solution_model, headloss types and the pump table.

WWNet · features and work in progress

CI builds and tests every push: Rust on Ubuntu and Windows, the toolbox and shared core, the wheel, the full bundle with a Pro-like smoke test, and the update zip. A Rust change needs the full bundle; a Python-only change goes out as the small update zip. On the antivirus: no detection name was available, so the likely causes were addressed rather than guessed at. If it is still flagged, the path is an IT allowlist by SHA-256 and, permanently, code signing.
